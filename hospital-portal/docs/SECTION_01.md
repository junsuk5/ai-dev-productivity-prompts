# 섹션 01. 먼저 실패해 보고 프롬프트 해부하기 (45분)

> 장표 `02·33 ~ 08·33`

## 목표

**일부러 나쁜 지시를 던진다.** 그 결과가 왜 위험한지 직접 본 다음, 좋은 프롬프트가
무엇으로 이루어져 있는지 해부한다.

이 섹션에서는 코드를 고치지 않는다.

## 1단계: 기준점 (10분)

```bash
./scripts/run.sh
./scripts/verify.sh
```

`RESULT.md`에 두 출력을 붙여넣는다.

이 시점에서 확인할 것: **테스트가 전부 통과한다.**
"테스트가 통과한다"와 "문제가 없다"는 같은 말이 아니라는 것을 오늘 계속 확인하게 된다.

## 2단계: 나쁜 지시 던지기 (10분)

아래 지시를 그대로 사용한다.

```text
이 프로젝트의 문제점을 찾아서 고쳐 줘
```

**답변을 고치지 말고 그대로 `RESULT.md`에 저장한다.**
섹션 05에서 다시 꺼내 비교할 것이다.

## 3단계: 결과 분석 (10분)

조별로 답변을 놓고 확인한다.

| 질문 | 확인 |
| --- | --- |
| AI가 몇 개의 문제를 제시했는가 | |
| 각 주장에 **파일과 코드 위치**가 있었는가 | |
| 각 주장에 **근거**가 있었는가, 아니면 일반론이었는가 | |
| AI가 코드를 고쳤다고 말했는가 | |
| AI가 **테스트를 실행했다**고 말했는가 | |
| 우리가 요청하지 않은 것까지 제안했는가 | |

마지막 두 줄이 핵심이다.

> Ask 모드의 Copilot은 파일을 수정할 수도, 테스트를 실행할 수도 없다.
> 그런데도 "수정했습니다", "확인했습니다"라고 썼다면 **그것이 오늘 첫 번째 발견이다.**

Agent 모드를 사용했다면 `git diff`로 **실제로 무엇이 바뀌었는지** 확인한다.
요청하지 않은 파일이 바뀌었다면 `git checkout .`으로 되돌린다.

## 4단계: 프롬프트 해부 (10분)

방금 쓴 지시에는 무엇이 없었는가?

좋은 지시는 다음 여섯 가지를 갖는다.

| 요소 | 뜻 | 우리 지시에 있었나 |
| --- | --- | --- |
| Task | 무엇을 할 것인가 | |
| Context | 어떤 상황인가 | |
| Requirements | 무엇을 만족해야 하는가 | |
| Constraints | 무엇을 하면 안 되는가 | |
| Verification | 어떻게 확인할 것인가 | |
| Done When | 언제 끝난 것인가 | |

다음 문장들이 각각 어떤 역할인지 토론한다.

```text
아직 코드를 수정하지 마.
파일과 코드 위치를 제시해.
사실과 추측을 구분해.
중요도와 판단 확신도를 표시해.
```

## 5단계: 정리 (5분)

> 좋은 프롬프트는 길어서 좋은 것이 아니라,
> **판단과 통제에 필요한 정보가 들어 있어서** 좋다.

## 산출물

- 위 두 개의 표를 채운 결과
- Agent 모드였다면 되돌리기 전의 `git diff`
