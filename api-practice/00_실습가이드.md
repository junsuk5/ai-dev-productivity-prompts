# 오전 실습 — 공개 API 3종 코드 초안 작성

건강보험심사평가원(HIRA) 공개 API 3종의 명세를 해석해서 호출 코드를 작성합니다.
프로젝트 스캐폴딩 없이 진행합니다. 언어·프레임워크는 자유입니다(Java, Python, Node 등
편한 것을 씁니다).

명세만 보고 바로 코드를 시키지 않습니다. **요건정의 → 태스크 분해 → 규칙 → 개발지시
→ 사람 리뷰** 순서로 진행합니다. 공공기관 시스템은 코드보다 이 절차와 문서가 더
오래 남기 때문입니다.

## 순서

| 순서 | 서비스 | 역할 | 시간 |
| --- | --- | --- | ---: |
| 1 | 병원코드정보서비스 | **데모** — 5단계 전부 같이 본다 | 60분 |
| 2 | 수가기준정보조회서비스 | **실습 1** — 룰은 재사용, 나머지는 혼자 | 45분 |
| 3 | 질병정보서비스 | **실습 2** — 힌트 없이 스스로 재현 | 45분 |

뒤로 갈수록 문서 작성 부담이 줄어듭니다. 데모에서 만든 `RULES.md`를 실습1·2에서
계속 재사용하는 것 자체가 오늘 배우는 것 중 하나입니다 (반복 절차를 규칙으로 저장해
두면 다음부터 다시 안 써도 된다는 것).

## 5단계 공통 절차

| 단계 | 산출물 | 목적 |
| --- | --- | --- |
| 1. 요건정의서 | `REQUIREMENTS.md` | API 명세를 조직 문서 포맷으로 번역 |
| 2. 태스크 분해 | `TASKS.md` | 진척 관리 단위로 쪼갬 |
| 3. 베스트 프랙티스 룰 | `RULES.md` | 이후 모든 개발지시가 따라야 할 제약 |
| 4. 개발 지시 | 코드 | 1~3의 문서를 컨텍스트로 넣은 구현 요청 |
| 5. 사람의 리뷰 | 체크 표 | 요건 충족·룰 준수·실행 결과 판정 |

각 단계 프롬프트는 **한 번에 붙여넣습니다.** 나눠서 여러 번 묻지 않습니다.

## 완료 조건 (3개 서비스 공통)

```text
[ ] REQUIREMENTS.md에 기능 요건·파라미터표·응답표·예외 케이스가 있다
[ ] TASKS.md의 각 태스크에 완료 조건이 관찰 가능한 형태로 적혀 있다
[ ] RULES.md의 규칙을 어긴 부분이 있으면 표시했다
[ ] 실제로 실행해서 응답(또는 오류 메시지)을 눈으로 확인했다
```

**"코드가 그럴듯해 보인다"는 완료 조건이 아닙니다. 문서와 실행 결과가 근거입니다.**

## 1. (데모) 건강보험심사평가원_병원코드정보서비스

`https://www.data.go.kr/data/15001697/openapi.do?dType=API`

5단계 전부를 실제로 진행하는 과정을 봅니다. 보면서 **어떤 정보가 각 문서에 들어가야
다음 단계가 헤매지 않는지** 관찰합니다.

### 1단계 — 요건정의서

```text
[Task] 아래 공공데이터포털 API 명세를 요건정의서 형태로 정리해 줘.

[Context] 서비스명: 건강보험심사평가원_병원코드정보서비스
API 명세: (요청 URL, 파라미터 표, 응답 구조 원문을 여기 붙여넣는다)

[Requirements]
- 기능 요건: 이 API로 얻어야 하는 결과를 한 문단으로
- 요청 파라미터 표: 이름/타입/필수여부/설명
- 응답 필드 표: 이름/타입/설명
- 예외 케이스 목록: 명세의 오류 코드와 의미
- 비기능 요건 후보: 타임아웃·재시도·로깅 유의점을
  "명세에서 확인됨" / "일반적 권장(확인 필요)"로 구분

[Constraints] 아직 코드를 작성하지 마. 문서만 작성해 줘.
[Done When] 위 다섯 항목이 채워지면 끝.
```

**사람이 명세와 대조해서 승인해야 다음 단계로 간다.**

### 2단계 — 태스크 분해

```text
[Task] 승인된 요건정의서를 바탕으로 개발 태스크 목록을 만들어 줘.
[Context] [1단계에서 승인된 REQUIREMENTS.md 전체]
[Requirements]
- 작은 단위로 쪼개라 (요청 함수 / 응답 파싱 / 예외 처리 / 실행 확인)
- 각 태스크: 산출물, 완료 조건(관찰 가능한 형태), 선행 태스크
- 표로 정리
[Constraints] 아직 코드를 작성하지 마.
[Done When] 태스크 표가 요건정의서 전 항목을 빠짐없이 커버하면 끝.
```

### 3단계 — 베스트 프랙티스 룰

```text
[Task] 이 API 연동 코드가 지켜야 할 규칙을 정의해 줘.
[Context] 공공기관 시스템 연동 코드이고, 이후 다른 API에도 재사용할 규칙이야.
[Requirements] 각 항목 한 줄로:
- 인증키 관리 방식 / 오류 응답 처리 방식 / 로그 금지 정보
- 외부 라이브러리 사용 범위 / 네이밍 규칙
[Constraints] 아직 코드를 작성하지 마.
[Done When] 다섯 항목이 채워지면 끝.
```

이 룰을 만들기 전에 4단계를 먼저 시키면, 서비스 키가 코드에 그대로 박히는 걸 보게
됩니다. 룰을 만든 뒤 같은 4단계를 다시 던져서 차이를 비교합니다.

### 4단계 — 개발 지시

```text
[Task] TASKS.md의 태스크를 순서대로 구현해 줘.
[Context]
### 요건정의서
[REQUIREMENTS.md]
### 태스크
[TASKS.md]
### 규칙
[RULES.md]
[Requirements] 태스크 순서대로, 완료할 때마다 어떤 태스크인지 표시하며 진행해 줘.
[Constraints] RULES.md를 반드시 지켜라. 위반하면 위반 사실을 먼저 말해라.
[Verification] 실행 가능한 상태로 줘. 실행은 내가 한다.
[Done When] TASKS.md의 모든 태스크가 구현되면 끝.
```

### 5단계 — 사람의 리뷰

요건정의서 항목별 충족 여부 / 룰 위반 여부 / 실행 결과(성공·오류)를 표로 사람이
직접 채웁니다.

### 6단계 — 저장 (재사용 준비)

`REQUIREMENTS.md`의 템플릿 구조, `RULES.md` 전체, 4단계 프롬프트 틀을 파일로
저장해 둡니다. 실습 1·2에서 다시 씁니다.

## 2. (실습 1) 건강보험심사평가원_수가기준정보조회서비스

`https://www.data.go.kr/data/15021028/openapi.do`

**`RULES.md`는 데모에서 만든 것을 그대로 재사용합니다.** 3번 프롬프트(룰)는 생략하고
1·2단계를 프롬프트 1개로 합쳐서 진행합니다.

```text
[Task] 아래 API 명세로 요건정의서와 태스크 목록을 함께 작성해 줘.
[Context] 서비스명: 건강보험심사평가원_수가기준정보조회서비스
API 명세: (붙여넣기)
[Requirements] 1부는 요건정의서(기능 요건/파라미터표/응답표/예외 케이스),
2부는 태스크 표(산출물/완료 조건/선행 태스크)로 나눠서 작성해 줘.
[Constraints] 아직 코드를 작성하지 마.
[Done When] 두 문서가 다 나오면 끝.
```

사람이 승인한 뒤, **4단계(개발 지시)를 데모와 같은 틀로** — 단 `[Context]`의
`RULES.md`는 데모 때 저장해둔 걸 그대로 붙여넣습니다. 5단계(리뷰)도 데모와 동일하게
진행합니다. 총 3회 프롬프트(요건+태스크 / 개발지시 / 없음 — 리뷰는 사람이 직접).

## 3. (실습 2) 건강보험심사평가원_질병정보서비스

`https://www.data.go.kr/data/15119055/openapi.do`

이번에는 프롬프트 틀을 보지 않고 **스스로 5단계를 재현**합니다. 시간이 부족하면
요건정의서만 짧게 쓰고 태스크는 구두로 넘어가는 것도 괜찮습니다. 목표는 완성이 아니라
절차를 몸에 익히는 것입니다. 오후 섹션 01에서 이 절차의 각 요소(Task/Context/
Requirements/Constraints/Verification/Done When)가 왜 필요한지 다시 다룹니다.
